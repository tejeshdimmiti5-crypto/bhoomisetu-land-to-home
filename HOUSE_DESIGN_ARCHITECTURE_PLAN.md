# House Design Architecture Plan

Status: planning document for the feature branch. This document describes intended work; it does not claim the planned features are implemented.

## Current verified baseline

The current `/design` page uses Next.js, React, TypeScript, CSS, and SVG for an editable 2D room-rectangle preview. It supports room name and dimension editing, add/remove room, localStorage save/restore, JSON import/export, saved-plot selection from browser IndexedDB, plot-boundary overlay, and a geometric room-fit check. The repository's current CI includes lint, geometry, plot-store, floor-plan, plot-fit tests, TypeScript type-check, and production build.

Current limitations:
- The floor plan is a rectangle-based concept editor, not CAD/BIM.
- It does not model wall thickness, doors, windows, stairs, plumbing, electrical, structural members, or building-code rules.
- Plot fit is a geometric estimate only. It does not assess legal boundaries, setbacks, easements, access, structural safety, or permit compliance.
- Local browser persistence is not account-based cloud sync.
- A print/PDF action has been added, but its browser output still needs validation and CI must pass on the latest commit before the change is treated as verified.
- There is no integrated 3D engine yet.

## Non-negotiable correctness rules

1. One canonical design model must drive 2D, 3D, validation, and exports. Do not maintain separate independent 2D and 3D room data.
2. Store lengths in metres and positions in a documented local plan coordinate system. Convert only at UI/export boundaries.
3. Do not silently move, resize, delete, or normalize a user's room. If geometry is invalid, show a clear error and preserve their editable input when safe.
4. Make coordinate origins and transformations explicit. Plot overlay and room-fit calculations must use the same transform.
5. Never claim that GPS measurements are legal survey data. Preserve method and accuracy/provenance metadata where available.
6. Distinguish geometric validation from architecture, structural engineering, legal, and building-code review.
7. Import is untrusted input: validate schema, numeric bounds, unique IDs, size limits, and supported versions before applying it.
8. Keep local storage and export/import working even if optional 3D rendering fails.
9. Do not add a large dependency until the feature needs it; pin/lock dependencies reproducibly before relying on CI installs.
10. Do not merge to `main` without explicit user approval.

## Target architecture

### Canonical model
Create a versioned `HouseDesignDocument` model containing:
- schema version and stable design ID
- design name and timestamps
- explicit unit (metre) and coordinate convention
- optional linked plot ID and a snapshot/reference policy
- rooms with stable IDs, names, positions, width, depth, and later height/level
- later: walls/openings/materials as distinct typed entities rather than encoding them as room rectangles

The existing `FloorPlanRoom` shape is the current MVP model. Introduce a versioned shared document incrementally; preserve backwards-compatible import of the current version.

### Rendering layers
- 2D: keep SVG and make it a projection of the canonical model.
- 3D: when introduced, use Three.js through React Three Fiber. Use the same canonical model and explicit metre-to-world-unit transform. Keep 3D read-only initially; editing remains in the proven 2D editor until synchronization and tests are in place.
- UI controls: React components, TypeScript, current CSS design system.
- Geometry: pure TypeScript functions independent of React/DOM, with unit tests.
- Persistence: current browser-local save remains supported; migrations must be explicit.

## Safe implementation phases

### Phase 0 — Stabilize current branch
- Confirm all current CI runs finish successfully for the latest commit.
- Manually check print output in a browser when possible.
- Add/keep regression tests for room validation, overlap, plot containment, and import rejection.
- Introduce a reproducible dependency lockfile only when generated by a real npm install in an environment with registry access; then use `npm ci` and setup-node caching.

### Phase 1 — Canonical design document
- Add typed, versioned document model and validation/migration functions.
- Keep the existing editor behavior and legacy saved-plan import working.
- Add tests for invalid data, duplicate IDs, bounds, unknown schema versions, and migration behavior.
- Do not add 3D yet.

### Phase 2 — Better 2D editing
- Add explicit grid/snap settings, coordinate axes, dimensions and clearer validation feedback.
- Keep all snap/transform logic deterministic and unit-tested.
- Add room-fit status that distinguishes invalid geometry, room overlap, and plot-boundary fit.

### Phase 3 — Read-only 3D preview
- Add Three.js / React Three Fiber and compatible helpers after dependency/lockfile work is clean.
- Build simple floor slabs and wall placeholders from the canonical document.
- Add orbit, zoom, reset-camera, and 2D/3D toggle.
- Keep rendering failure isolated; 2D edit/save/export must still work.
- Test that 2D and 3D use the same dimensions and transforms. Label the model as conceptual.

### Phase 4 — Architectural entities
- Add walls, openings, and floor levels as explicit data structures with geometry tests.
- Avoid claiming construction readiness without professional review and validated code/rule sources.
- Add formats such as SVG/PDF first; consider DXF/IFC only with explicit scope and tested exporters.

### Phase 5 — Real-world integrations
- Land value, flood risk, supplier/contractor data, and construction tracking require authoritative sources, freshness/provenance, geographic coverage, and clear unavailable/unknown states.
- Contractor certification must link to actual verifiable credentials and issuing authorities; never infer certification from a listing.
- Voice and multilingual AI can assist with input, but must not silently modify geometry or make engineering/legal decisions.

## Acceptance gates for each implementation PR

- Scope states what changed and what did not change.
- Lint passes.
- All geometry and storage regression tests pass.
- TypeScript type-check passes.
- Production build passes.
- Relevant edge cases have tests.
- No fake external data, fake certifications, or unverified test claims.
- UI labels prototypes and estimates honestly.
- Feature branch stays separate; no merge to `main` without explicit approval.
